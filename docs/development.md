# Development, tests, release

Layout of the repository, how the tests run, and how a release reaches the sandbox. Back to the [README](../README.md).

## Layout

```
src/            engine: config, sources (folder, S3), readers (CSV, NDJSON, Bundle), transform worker,
                FHIR delivery, pipeline, the source manager, API, alerts, storage
hie_runtime/    Python side of the transform protocol (worker.py, hie.DataError) and the pinned
                launcher it runs under (limits.py, limits.pin)
transforms/     Python transforms: lab_results.py (CSV to Observation), fhir_passthrough.py
sources/        one YAML file per source; the API writes here too
examples/data/  sample files used by the tests and the demo
tests/          end-to-end Rust tests with a stand-in FHIR server; Python tests for the transform
docs/           design decisions
```

## Tests

```sh
cargo test                                 # unit tests and the end-to-end tests
python -m unittest tests/test_lab_results.py tests/test_hl7.py tests/test_terminology.py tests/test_worker.py
cargo clippy --all-targets -- -D warnings
# the build without a secret store (no default features), as CI runs it:
cargo clippy --all-targets --no-default-features -- -D warnings
cargo test --no-default-features --lib --test secrets --test no_backend_startup --test check --test s3_credentials
```

The end-to-end tests run the real Python transforms against a stand-in FHIR server. `tests/pipeline.rs` covers a folder source: the outage and recovery, the duplicate file and the re-sent rows, each kind of bad row, reprocessing with a correction, the silence alert, and a load whose rows were all filtered out raising no alert while a mixed load's alert counts its failing rows, again only when more of them fail than at its previous finish (a load whose failing rows were fixed and that later fails again alerts again). `tests/events.rs` covers the event log: each outcome stored with its event before the next record is sent (the stand-in FHIR server reads the log through its own store handle on every request) or transformed (the probe transform reads the SQLite file), nothing stored when the event cannot be (a SQLite trigger refuses it, for an admission and for a delivery), outcomes for a record put back while it was transformed or sent changing nothing, a transform that cannot finish now (logged once per reason and runner), a submission opened, failing a poll, settled by its receipts or refused with an answer that echoes signed URLs and the engine's own path, a submission not opened when a record changed while it was written (on both bulk paths), a Retry, a refusal and an unsendable file of 450 rows each (more than one chunk), an older answer that cannot roll a record's attempts back, a submission claimed before each kick-off and poll (a late kick-off answer after its attempts went 0, 1 and back to 0 changes nothing, whatever it says; of two runners in flight the last claim decides; a row read before another runner moved it cannot be claimed; an earlier version's write still fences a claim), content taken meanwhile not admitted twice, a Retry that finds nothing, a finish reporting failing rows beyond those its previous finish left (a fix lowers the mark, so a regression is reported again), the API's paging, filters, cursor and refusals (and, in `src/db.rs`, a request reading at most its span of the log: a rare filter answered with empty pages that go on to its match, dense matches paged by `limit`, a purged gap that costs nothing, and `since` listing an earlier id stored after it), the retention purge (old events and alerts, the alerts kept, the highest alert id kept so no id is given again, the alert counter unchanged, two purges at once counted once, more than one chunk) a restart that stops the first engine for good, distinct rejected records per day (a record rejected twice once, filtered rows apart, a midnight event in the day it starts, coverage from when the log began, within the retention, and after what another instance with a shorter retention purged) and that start kept across a reopen; with `HIE_TEST_DATABASE_URL`, an event committed later with a lower id never skipped by a reader, a finish that waits for a Retry's row lock (and one that counts the failing rows committed while it waited), an alert cleared while the purge waits for it kept, a record put back while its file is rejected left as it was put back, each test waiting until PostgreSQL shows the lock wait. `tests/alerts.rs` covers the rules: the one a source is born with and that a replace does not bring back, the CRUD, and the `rejected_share` and `silence` rules firing once and clearing, `rejected_share` weighing the failing rows among those a load kept (a load that kept none neither fires nor clears it); and rule ids never given again (after a delete, a reopen, and on a SQLite store whose rules table was made the old way), with `created_at` set by the engine; and reading alerts by period and in pages: `since` at its boundary (as the list returns it, finer, with an offset), every combination with `source` and `open` walked at several page sizes, a walk that keeps its place while alerts are added, cleared and removed, the default page of 100, the largest of 1000, and malformed queries (a negative `limit` or one above 1000 among them) refused without echoing them, on SQLite and, with `HIE_TEST_DATABASE_URL`, PostgreSQL; and, through the pipeline and the API, the webhook's delivery state: an alert from before events were recorded cleared and delivered, signed, with the API's time strings, events waiting for this URL (`pending`) and for another (`parked`), a `fired` parked for another URL still listed in `webhook.events` after its `cleared` was delivered, an alert with two events counted once in a page, a rule without the `webhook` channel (`not_requested`), an engine without a URL (`not_configured`), and no URL, secret or fingerprint in the answer. `tests/alert_webhook.rs` drives the webhook sender against a local receiver under the production log filter at `trace`: the signature over each attempt's `X-HIE-Timestamp` and the raw body (a signature over the body alone does not match, and a retry a second later is stamped and signed again over the same body), fired before cleared, one `event_id` and one body over retries, giving up after five retries, a redirect refused, an unreachable receiver, one that does not answer in time, two instances on one store sending each event once, an attempt whose outcome was lost sent again unchanged by another instance, and an event waiting for its own URL across restarts; no URL, secret or receiver answer reaches a log line or the store. Unit tests pin the HMAC to RFC 4231 and the signed string to a value computed independently (Python's `hmac`), the webhook secret read without the whitespace around it, and, in the store, with time passed in and two handles on one file, the claim, the fence against late outcomes and replacement rows, the last attempt with no outcome, the order of fired and cleared per URL, and the alert and its event written or rolled back together. `tests/check.rs` checks that `hie check` refuses bad `alerts:` settings without printing the URL or the secret. `tests/bulk_submit.rs` drives both bulk paths against a stand-in consumer: an NDJSON export handed over as source objects, and a lab CSV transformed, given derived ids, written by the engine and settled by receipts. Against a stand-in public bucket it checks that an anonymous source reading a whole bucket hands over each object's public URL with its key encoded once, every read unsigned and the engine's file route unused; that a store object is never served from that route, even when a local file shares its key, while a staged zip entry is; that keys and entries stay apart under a relative bulk directory; that entries staged by an earlier version are recognised at start-up, served, settled and retried, whether the engine starts from a relative or an absolute configuration path; that an archived folder file from an earlier version is served again on retry; and that a file taken from a bucket and retried after its source became a folder is rejected rather than served. `tests/bulk_logs.rs` runs under the production log filter asked for everything at `trace`: a failing poll, a refusal that echoes signed URLs (one on a bracketed IPv6 host, one with parentheses in its path) and the engine's own path with the token, a relative status target that carries a signature, a cleanup that cannot remove a submission's files, a token endpoint failure and a status URL stored during a working delivery (a statement parameter on PostgreSQL) keep signatures and tokens out of every log line, the alerts, the stored errors and answers, and the event log. A folder file recorded through a symbolic link and `..` is served as the filesystem resolves that path. With an in-memory store it checks that a URL that cannot be signed yet keeps its records pending while open submissions are polled, and that an object no configuration can hand over is rejected without stalling the pass. `tests/object_source.rs` covers the object-store path the S3 source uses, with an in-memory store; `tests/sqs_source.rs` adds a notification queue to it, against a stand-in SQS that checks the SigV4 headers: the bucket listed once at start, then only announced objects taken, with their messages deleted after the pass and test events, foreign keys, gone objects and keys that are not object paths consumed without effect; `tests/overlap.rs` checks that HFS receives the first Bundle well before a slow transform finishes the file; the same source was run by hand against a MinIO (the `ghcr.io/coollabsio/minio` mirror HFS's CI pins) holding the Synthea export, on both delivery paths against an HFS that requires tokens: 632 resources by REST and the same 632 by `$bulk-submit` through pre-signed URLs, each resource stored once, objects archived under the processed prefix, and a re-uploaded file recognised as a duplicate. `tests/fhir_server_source.rs` covers pulling another FHIR server: pages followed, a cursor per type that moves once the records are stored, nothing pulled twice, the token on every call, and the connection test. `tests/database_source.rs` covers the database source on SQLite: runs of the query past a cursor, the cursor moving once the rows are stored, nothing read twice, `cursor_start`, and the connection test; `tests/mssql_source.rs` runs the same source against a SQL Server when `HIE_TEST_MSSQL_URL` is set, and is skipped otherwise. `tests/leases.rs` puts two instances on one store: one runs the source, the other stands by, and takes over when the lease lapses. `tests/test_terminology.py` covers the terminology helpers against a stand-in HTS and the lab transform using them. `tests/zip_drop.rs` covers zips: a drop in a read-only bucket unpacked once and left in place, and one in a folder unpacked and archived, with a broken zip reported. `tests/hl7v2.rs` covers HL7 v2: a file of messages through a folder source, and messages over MLLP spooled, acknowledged, delivered, and resent as duplicates; `tests/test_hl7.py` covers the Python helpers. `tests/api.rs` drives a source through the API: test, create, check now, pause, resume, replace, delete, a deleted source's outage and credential alerts ended once its runner has ended and alerts left under its id ended before a source created again runs (another kind, one raised after the create and one while another instance holds the source left open), and its contact read from a file and from the API, kept by a replace that sends back what it read, cleared by one without it, and refused when too long or more than one line. `tests/loads.rs` covers the loads list across sources: the fields of the per-source list, newest first, each `status` filter and `failed` (unreadable, rejected rows while in progress or done, rows filtered out on purpose that do not count, and what takes a load out), a walk by cursor while loads arrive and leave the filter, the limits and the refused queries, a store written by an earlier version (its loads with no mark of failing rows), and a deleted source whose id is created again; a parameter the list does not read and a source's own list beyond 1000 loads refused; a unit test checks that SQLite chooses each page through an index, and one in `src/db.rs` that the store is free between two loads' reads, another caller's write landing there and seen by the next load. `tests/check_outcome.rs` drives the scans of a source another instance holds by hand: concurrent checks answered by the one scan after them with its one load, a check asked for once a scan started answered by the next with what the earlier one took, nothing new, a folder that cannot be listed (a fixed reason, no path), an unknown check, a replaced source's runner answering earlier checks, and a paused or deleted source failing them, but not one another instance still holds; the loads paged with the answer's cursor, malformed parameters refused with `invalid_query` and `field`, and the retention purge removing old checks, answered or not (`tests/events.rs` adds, on PostgreSQL, a check purge that waits for another instance's and moves on to the next old rows); unit tests in `src/db.rs` cover the snapshot, the first answer staying, pages of loads and the purge. `tests/check.rs` runs `hie check`: it refuses to start while `hie.yaml` has a `runtime` key or `HIE_RUNTIME_URL` is set, and passes when the variable is unset or blank; The default rule's birth is tested on both stores too: given once, not again after a replace, a failed start, a restart or a file put back, given again by a create and kept when its write or start fails, never twice when two handles race (one held inside its transaction while the other waits), a start of a born source answered while another handle holds SQLite's write lock, nothing recorded or published when it fails, and sources an earlier version left marked born without a rule. `tests/s3_credentials.rs` signs against a stand-in bucket that records key ids: the Test, the source, a rotation, the queue, an alert raised once and cleared, and a source waiting for its credential while its submissions are polled (a check asked for meanwhile fails, saying the credential is not loaded). `tests/secret_refs.rs` puts two engines on one store; `tests/secrets_canary.rs` checks that a canary secret appears in no answer, log line at `trace`, source file or database byte. `tests/worker.rs` runs the real launcher over a small test program for the long-lived worker cases of the `limited-process@1` contract (answers in order from one process, a reply written in pieces, a deadline and a late reply, a worker that exits or stays silent before it is ready, one that stops reading) and the engine's own duties: the pin check, setup errors, a stray line on stdout, the stderr tail, the run directories, the limits, the process group, the environment and cancelled calls; `tests/pipeline.rs` adds rows that hang, crash or run out of memory, each rejected once with the rows after it delivered, and `tests/api.rs` the bound on concurrent tries. `tests/worker.rs` also runs the real `hie_runtime/` with transforms that write to file descriptor 1 directly and through a child process, every record still getting its own reply. `tests/test_worker.py` checks the worker over its pipes (a write to file descriptor 1 included) and, on Linux, under the launcher's memory limit.

They are skipped if no Python 3.9+ is found; set `HIE_TEST_PYTHON` to point at one.

## Release and deploy

A version tag (`v0.1.0`) runs `.github/workflows/release.yml`, modelled on the HFS release chain (see [RELEASING.md](../RELEASING.md) for how to cut one):

1. **Build**: the Linux x86_64 release binary, packaged with `hie_runtime/`, `transforms/`, `sources/` and `examples/` as `hie-{version}-x86_64-unknown-linux-gnu.tar.gz`.
2. **Release**: a GitHub Release with the archive and its SHA-256.
3. **Image**: `ghcr.io/heliossoftware/hie:{version}`, `:{major.minor}`, `:sha-{sha}`, and `:latest` for a non-prerelease.
4. **Deploy**: from the `Deploy` runner over SSH to the host behind `hie.heliossoftware.com`: the binary and runtime go to `/opt/hie`, a systemd unit `hie` runs it on `0.0.0.0:8090`, and the job fails unless `/health` answers. `data/` and anything created through the API in `sources/` and `transforms/` survive a deploy.

Secrets the deploy needs: `HIE_DEPLOY_HOST`, `HIE_DEPLOY_USER`, `HIE_DEPLOY_PORT` (optional) and `HIE_FHIR_BASE_URL` (defaults to the public HFS). The public sandbox at `hie.heliossoftware.com` is deployed open, like the public HFS: a place to show the work and run demos, with nothing sensitive on it. A secure environment adds `HIE_AUTH_JWKS_URL`, `HIE_AUTH_ISSUER` and `HIE_AUTH_AUDIENCE` for the API, and `HIE_FHIR_TOKEN_URL`, `HIE_FHIR_CLIENT_ID`, `HIE_FHIR_CLIENT_SECRET` (and `HIE_FHIR_SCOPE`) for the engine's calls to HFS; the deploy writes them to the root-only `/etc/hie/hie.env` on the host.
