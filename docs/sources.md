# Sources

A source is one connection: where the data comes from, its format, the transform that turns it into FHIR, how it is delivered, and how often data is expected. Back to the [README](../README.md).

## Sources

A source is one connection: where the data comes from, its format, the transform that turns it into FHIR, how it is delivered, and how often data is expected. Each source is one YAML file in `sources/`, which the engine reads at start and **writes when a source is created or replaced through the API**, so definitions stay under version control either way.

```yaml
id: lab-results
name: Lab results
contact: "Lab IT on-call, +1 555 0100"   # optional: who to call about this source
source:
  type: folder               # or s3 (see sources/synthea-s3.yaml.example)
  path: inbox/lab-results
  pattern: "*.csv"
  poll_seconds: 5
format: csv                  # csv (default), ndjson, fhir_bundle, fhir or hl7v2
transform: transforms/lab_results.py
delivery:
  batch_size: 100            # entries per batch Bundle
  initial_backoff_ms: 2000   # doubles per failed attempt, up to 5 minutes
  alert_after_attempts: 5
expect_every: 24h            # the silence rule the source is born with
```

`contact` says whom to call about the source: one line of free text (a team, a person, a phone number, an address), at most 500 characters, shown as it is and never interpreted. The engine sends nothing to it and does not read it as an address. The text, as decoded, may not hold control characters (Unicode category Cc: a tab, a line break, an escape), the line and paragraph separators U+2028 and U+2029, or the bidirectional marks U+061C, U+200E and U+200F and embedding, override and isolate controls U+202A to U+202E and U+2066 to U+2069. A contact written through the API may not hold the invisible format characters either: U+200B (zero width space), U+2060 to U+2064 (word joiner, invisible operators), U+206A to U+206F (deprecated shaping controls) and U+FEFF (byte order mark). A source file that already holds one (saved by a build that took them) is still loaded as it is, with a `warn` log naming the source, and a change through the API refuses it until it is removed. The zero width joiner and non-joiner (U+200D, U+200C) are allowed, as scripts and emoji need them. So a YAML block scalar that keeps a line break (`|`, `>`) is refused, while a plain value folded over several lines is one line. Leaving it out, `null`, or a blank value (only whitespace) means no contact, and a blank one is not written. In YAML, quote a contact that would read as a number or `true`/`false` (`contact: "5550100"`): a bare one is refused, because it is not text. It is returned as `contact` wherever the source is read, `GET /api/monitoring/status` included, and edited with the rest of the definition: `PUT /api/sources/{id}` replaces the whole definition, so a body without `contact` leaves the source with none, and a client that changes one member sends back the `definition` it read, contact included. A contact in a source file is read at start like any member; an invalid one stops `hie run` and `hie check`, naming the file, and `hie check` prints each source's contact.

An S3 source names a `bucket`, an optional `prefix`, and an `archive_prefix` (default `processed`) that acknowledged objects are moved under. `endpoint` points at an S3-compatible store such as MinIO; `region` defaults to `us-east-1`. It says how it reaches the bucket with exactly one of:

- `credential: <name or id>`: a credential stored through [`/api/secrets`](api.md#secrets) (an access key id and secret access key). The source always uses its **current revision**: after a `PUT /api/secrets/{id}` it loads the new one on its next pass (at once with `check-now`), registers itself for it so the credential cannot be deleted while used, and lists the bucket in full on that pass. Until a revision has been loaded (a credential not stored yet, or deleted), a `credential` alert stays open, nothing is listed or handed over, and what is already submitted is still polled and settled. When loading a new revision fails after an earlier one was loaded, the source keeps working with the earlier one, the `credential` alert stays open, and the next pass tries again. Either way the alert clears on the first pass that loads the current revision;
- `anonymous: true`, for a public bucket.

A definition with neither, or both, is refused (`400`, and at start a file that has neither stops the engine, naming the file). The engine reads no AWS credentials from its environment, profiles or instance metadata. To move an existing source: add `credential: <name>` to its file, start the engine, then `POST /api/secrets` with that name; the source loads it on its next pass, without another restart. The connection test (`POST /api/sources/test`) signs with the credential's current revision, so it proves the credential before the source exists.

`anonymous: true` reads a public bucket without credentials: requests are not signed, so there are no pre-signed URLs either, and on the bulk path each object is handed over by its public URL (virtual-hosted on AWS, `https://{bucket}.s3.{region}.amazonaws.com/{key}`; path style for a bucket name with a dot or under `endpoint`; the key encoded once, segment by segment). `read_only: true` is for someone else's bucket: nothing is moved or written there, and an object the engine has already taken is recognised by its name and size, then by its content, and left alone on later passes. A read-only source can read a whole bucket: an empty `prefix`, and `archive_prefix: ""`, which excludes nothing. Keys are read and handed over exactly as the bucket lists them. A `prefix` or `archive_prefix` that contains `%`, `~`, non-ASCII or other characters an object-store path escapes is matched in its escaped form; keep them to plain ASCII. When the source sets no `region` or `endpoint`, the ones in effect may come from the environment (`AWS_REGION`, then `AWS_DEFAULT_REGION`; `AWS_ENDPOINT_URL`, then `AWS_ENDPOINT`; and `AWS_VIRTUAL_HOSTED_STYLE_REQUEST`), which only say where the bucket is; an empty one is refused, since it cannot be unset and would make the public URL point elsewhere. An endpoint over plain `http` needs `endpoint:` on the source.

With a **notification queue** (`queue:` the URL of an SQS queue the bucket's `s3:ObjectCreated:*` events go to, directly or through SNS) a pass reads the queue instead of listing the bucket: only the announced objects are fetched, and their messages are deleted once the objects are in the store, so a pass that fails leaves them to be delivered again. The bucket is still listed in full at start and every `relist_seconds` (default 3600), so an object whose event was lost is taken within the hour rather than never. The queue is signed (SigV4) with the source's stored credential, so `anonymous` and `queue` do not go together; its region comes from the queue URL, else the bucket's region in effect, else `us-east-1`. The queue's visibility timeout should exceed a pass over the largest drop.

A **zip** that arrives on any file source is a drop of several files: every entry whose extension fits the source's format (`.csv`, `.ndjson`/`.jsonl`, `.json` for Bundles, `.hl7`/`.txt`, and all three JSON extensions for `fhir`) becomes a load of its own, named `drop.zip!/path/inside`; the other entries (a `README.md`, a CSV in an NDJSON drop, the manifest of an NDJSON export) are skipped. In a `fhir_bundle` source a `.json` manifest fits the format and is read as a Bundle, so it is unreadable; a `fhir` source skips it (see [FHIR files](#fhir-files)). The zip is recorded as `unpacked`, archived like any file, and not read twice. Entries are unpacked in memory, so a zip should hold a few hundred megabytes at most. On the `source_objects` bulk path HFS cannot read a zip, so each unpacked entry is **staged** where HFS can fetch it: in the source's own store under `{archive_prefix}/unpacked/` when the store can be written and can sign URLs, otherwise under the engine's `bulk_dir`, served at `/bulk/{token}/files/{n}`; staged entries go once the receipts are in.

A **FHIR server** source (`type: fhir_server`, see `sources/other-fhir.yaml.example`) pulls another server into HFS: it names the server's `url`, the resource `types` to pull, and optionally `since` (a FHIR instant to start from) and `auth` (`method: client_credentials` with `token_url`, `client_id`, `client_secret_env`, or `method: bearer` with `token_env`; secrets are read from the named environment variable, never written in the file). Each pass searches every type for `_lastUpdated=gt{cursor}` sorted by `_lastUpdated`, `page_size` per page and up to `max_pages` pages, and hands the resources on as one NDJSON load per type; the cursor moves to the newest `meta.lastUpdated` once the records are stored, so a crash repeats a page rather than losing it. The format is `ndjson` whatever the file says, resources go out by their id, and `bulk_submit` is refused. The connection test reads `/metadata` and counts what waits past each cursor.

A **database** source (`type: database`, see `sources/lab-database.yaml.example` and `transforms/sql_lab_results.py`) reads a SQL database with the operator's own query: `url_env` names the environment variable holding the connection URL (`postgres://`, `mysql://`, `sqlserver://` or `sqlite:`; the URL carries the password, so it is never in the file), `query` is the SQL with `{cursor}` where the cursor value goes, an `ORDER BY` on the cursor column and a `LIMIT`, and `cursor_column` is the column the cursor follows. Prefer a **unique, increasing column** such as an id: with an updated-at column, rows that share one timestamp (a multi-row `INSERT` gets a single `now()`) and fall on both sides of a `LIMIT` are never read, because the next run asks for values strictly past the cursor; the engine logs a warning when a whole run shares one cursor value. Each pass binds the cursor as a parameter, runs the query up to `max_runs` times moving the cursor between runs, and hands the rows on as one NDJSON load; each row reaches the transform as a JSON object with the database's types (numbers, ISO timestamps, JSON). The cursor keeps its kind (integer, float, timestamp, date, text) and moves to the largest value seen once the records are stored. `cursor_start` says where to begin the first time. PostgreSQL is the target; MySQL/MariaDB and SQLite go through the same code (the tests run on SQLite), and **SQL Server** through its own driver with the same definition: `sqlserver://user:password@host:1433/database?encrypt=on&trust_cert=true` (`mssql://` too; `encrypt` is on by default, `trust_cert=true` accepts a self-signed certificate; the placeholder is bound as `@P1`, and a `TOP n` plays the part of `LIMIT`). SQL Server authentication only; Windows authentication is not supported. The connection test connects and runs the query once past the cursor.

### FHIR files

`format: fhir` takes a drop of FHIR JSON files that mixes NDJSON and Bundle files, such as a FHIR bulk export delivered as a zip (see [`sources/fhir-export.yaml.example`](../sources/fhir-export.yaml.example)). On a folder or S3 source each loose file and each zip entry is read by its own extension: `.ndjson` and `.jsonl` as NDJSON, one resource per line; `.json` as a Bundle, one record per entry with references between entries by `fullUrl` rewritten to `Type/id`, or one record when the file holds a single resource. The extension decides, not the content: an NDJSON file saved as `.json` is unreadable when it holds more than one JSON document, and one holding a single resource on one line is read as that resource.

- A **bulk export manifest** (a `.json` object with no string `resourceType`, a string `transactionTime` and an array `output`) holds no resources. In a zip it is skipped like a README; as a loose file it is a load with no records, archived without an alert. Any other `.json` without a `resourceType` is unreadable, as with `fhir_bundle`.
- A **loose file with another extension** that the pattern takes is recorded `unreadable` with the reason `not an NDJSON (.ndjson, .jsonl) or JSON (.json) file`, raises an `unreadable_file` alert and is archived (a read-only bucket leaves it in place), like any file that cannot be read; its content is not guessed. So the pattern picks the drop: `"*.zip"` for zipped exports, `"*json"` for loose `.json` and `.ndjson` files (not `.jsonl`); `*`, the default pattern of folder and S3 sources, takes every file, and each foreign one fails with an alert.
- The resources go through as they are, so the transform must be the passthrough (`fhir_passthrough.py`); a definition with another is refused (`400`, and at start a file that names one stops the engine). Every resource is passed through, an `OperationOutcome` line of an export included, and one with neither `id` nor `identifier` is rejected. A reference to a Bundle entry with no `id` (only an `identifier`) stays `urn:uuid:…`, as with `fhir_bundle`.
- On `bulk_submit` HFS is handed the transformed resources, NDJSON per resource type (`auto` resolves to `transformed`): a Bundle file is not an NDJSON object HFS could fetch, so `bulk_from: source_objects` is refused.
- Content is recognised by its SHA-256, as in every source, but here a file counts as one already taken only under a name read the same way: a zip, NDJSON (`.ndjson` and `.jsonl` alike), a Bundle (`.json`), or any other extension. A file refused for its extension and dropped again with the same bytes under a name that reads it is read; the same bytes under another NDJSON name are a duplicate.

A FHIR server, database or MLLP source keeps its own format whatever the file says, `fhir` included.

### HL7 v2

`format: hl7v2` reads a file of HL7 v2 messages (one or more, each starting at its `MSH`; segments separated by `\r`, `\n` or `\r\n`) into one record per message. The record is a JSON object the transform reads without parsing pipes:

```json
{"message_type": "ADT^A01", "control_id": "MSG0001", "sending_application": "LAB", "sending_facility": "NORTH",
 "receiving_application": "HIE", "receiving_facility": "HFS", "version": "2.5.1",
 "segments": [{"name": "MSH", "fields": ["|", "^~\\&", "LAB", ...]}, {"name": "PID", "fields": ["1", "", "12345^^^NORTH^MR", "", "Doe^Jane^M", ...]}],
 "text": "MSH|^~\\&|LAB|..."}
```

Fields keep their separators; the helpers in `hie_runtime/hie.py` split them: `hl7(record, "PID-5.1")` (segment, field, component; `PID-3[2].1` for a repetition, `OBX(3)-5` for the third OBX), `hl7_segments(record, "OBX")`, `hl7_field(segment, "5.1")`, and `hl7_datetime("20261021120000")` for an HL7 timestamp as a FHIR `dateTime`. `transforms/hl7_adt_patient.py` turns an ADT A01/A04/A08/A28/A31 into a `Patient` delivered as a conditional update on the MRN in `PID-3`.

An **MLLP** source (`type: mllp`, see `sources/adt-mllp.yaml.example`) listens on `listen` (e.g. `0.0.0.0:2575`) for MLLP-framed messages. Every message is parsed, written to `spool` as its own file (written, fsynced, renamed), and **only then acknowledged** `AA`, so an acknowledgement means HIE has it. A message that cannot be stored is answered `AE` (the sender keeps and resends it); bytes that are not HL7 are answered `AR` and dropped. The spool is picked up every `poll_seconds` like a folder: one load per message, the same SHA-256 dedupe (a resent message is a duplicate, not a second update), the transform, delivery. The listener starts with the source and is retried, with an alert, when the port cannot be bound. There is no TLS on the listener; put it behind a TLS proxy or a VPN as MLLP usually is. The connection test checks the port can be taken (when the source is not already listening) and counts what waits in the spool.

### Delivery methods

`delivery.method` picks how a source's records reach HFS:

- **`rest`** (default): the transform runs on every record and the resources go out in `batch` Bundles, one `PUT` per record, with a status per entry. For anything that needs a transform, and for feeds of hundreds to tens of thousands of records at a time.
- **`bulk_submit`**: HFS ingests through a `$bulk-submit` manifest the engine serves at `{public_url}/bulk/{token}/manifest.json`, polls the status URL, reads HFS's receipts (`{"reference": "Type/id"}` per stored resource, an `OperationOutcome` per failure) and maps them to its records by `Type/id`. What the manifest points at is `delivery.bulk_from`:
  - `source_objects`: for data that already is FHIR with ids, such as an NDJSON export. No transform runs. The engine stores the rows for the history, predicts what HFS will refuse (no `resourceType`, no `id`), and hands the **source objects themselves** over: pre-signed URLs for S3 objects, public URLs for the objects of an anonymous bucket, the engine's own `/bulk/{token}/files/{n}` for folder files and for the zip entries it staged itself. An object in a store is never served by the engine; only files the engine reads from disk or unpacked itself are. A URL that cannot be signed yet leaves the file's records pending for the next pass; an object no configuration can hand over (no signer and not a public bucket, or a file taken from a store whose source has since been replaced by one that reads from disk) has its records rejected with the reason. A bulk delivery failure is logged, alerted and stored with every URL in its reason cut to its origin (`https://host/…`): no path, query or user information. One submission per drop (up to `manifest_objects_max` objects), with a `submissionId` derived from the files so a repeated drop is refused by HFS instead of ingested twice. Objects stay at the source until the receipts are in, then they are archived.
  - `transformed`: for anything else, a lab CSV included. The transform runs as on the REST path; a resource that carries only an `identifier` gets an **`id` derived from it** (48 hex characters of SHA-256 over `system|value`), so `$bulk-submit`, which stores by id, updates the same resource every time the row is sent. The engine writes the resources as NDJSON per resource type, puts them in the source's own store when it can sign URLs (an S3 source: HFS fetches from the bucket, under `{archive_prefix}/submissions/{token}/`) or serves them itself from `bulk_dir`, and opens one submission per `bulk_records_max` records. The source file is archived as soon as it is read; the engine's files go once the receipts are in.
  - `auto` (the default): `source_objects` for `ndjson` or `fhir_bundle` with the passthrough transform, `transformed` otherwise (`fhir` included, which refuses `source_objects`).

  `url_ttl_seconds` bounds how long the URLs stay valid.

`public_url` in `hie.yaml` must be the URL HFS reaches the engine at.

With `delivery.stamp_source` on in `hie.yaml`, the REST path and `bulk_from: transformed` tag every resource with its source (`meta.tag` `urn:helios:hie:source|<source id>`); `bulk_from: source_objects` (or `auto` resolving to it) hands the objects over untouched and cannot. See [Tagging delivered resources with their source](running.md#tagging-delivered-resources-with-their-source).

The same document is what `POST /api/sources` takes. Before creating one, `POST /api/sources/test` with `{"source": {...}}` lists the connection once and answers with the evidence: reachable or not, in how many milliseconds, how many objects match, and the newest one.

### Alerts and rules

Alerts are governed by **rules**: data, created and edited over the API, each naming a source (or every source), a condition with its threshold, who to notify, and the channels (`app`, `webhook`, `email`). A new source is born with one `silence` rule set to its `expect_every` (two hours when it has none), so nobody has to remember to watch it. It is given only when the source is created: the first time the store sees it at a start, or by `POST /api/sources`. A replace or a restart never adds it back, so a deleted default rule stays deleted. A source deleted through the API and created again with `POST` gets it again (unless its old `silence` rule is still there); one whose file is put back is the source the store knew and does not.

| Condition | Threshold | Fires when | Clears when |
|-----------|-----------|------------|-------------|
| `silence` | a duration, `2h` | nothing has arrived for longer than that | data arrives |
| `missing_by` | a time of day, `06:00`, in the rule's `tz` (UTC without one) | that time passes and nothing arrived today | the file arrives |
| `rejected_share` | a percentage, `10%` | more than that share of the rows a load kept fail: rows its transform filtered out on purpose are left out of both counts | a later load that kept rows is within the limit |
| `unreachable` | a number of attempts, `5` | delivery to HFS has failed that many times in a row | delivery succeeds |

A `missing_by` rule may carry `tz`, an IANA time zone name, so that both its time and "today" are the zone's: `{"source_id": "lab-results", "condition": "missing_by", "threshold": "06:00", "tz": "Europe/Madrid"}`. The name is kept as the database spells it, and a rule without one (or with `"tz": null`) stays in UTC. Only `missing_by` takes a zone; a name that is not a zone, or a zone on another condition, is refused with `400`. Today runs from local midnight to the next. A time skipped by a change of offset (such as daylight saving time) is due at the change, the first valid moment after it; a time that happens twice is due at its first occurrence. When that pushes a deadline to the next midnight, the alert fires as the next day begins, for the day before, if nothing arrived that day; a rule made after that midnight does not judge the day before it. Like any open `missing_by` alert, it clears at the next pass that finds a file of the current day, with the reason naming that day (`Lab: a file arrived on 2026-03-29`): the alert was raised, and its webhook `fired` queued when the rule sends one, on the pass before, and a day's file shows the source delivering again. Changing a rule's `tz` ends its open alert, as a change of its threshold does (below).

A condition raises **one** alert per rule and source, open until it clears itself; the alert keeps its rule, who was notified, the channels, and the clearing time and reason. `app` alerts are what the UI lists; `webhook` sends the alert's two events, when it fires and when it clears, to `alerts.webhook_url` (below); `email` is accepted and recorded, with no mail sink wired yet. Alerts without a rule (an unreadable file, a skipped definition, a credential that cannot be loaded) go to the webhook too. Whether an alert's `cleared` event is posted follows the channels recorded on the alert when it fired, not the rule's channels now: an alert fired with `webhook` has its clear posted after the rule dropped `webhook`, and one fired without it does not after the rule added it. Turning a rule off, deleting it, or changing its condition, threshold, time zone or source through the API clears its open alerts in the same transaction (`its rule was turned off`, `its rule was deleted`, `its rule was changed`), each with its `cleared` event for the channels recorded when it fired; if the changed rule still finds the condition, it raises a new alert, with its own id (`silence` and `missing_by` at the next pass, `unreachable` at the next failed delivery, `rejected_share` at the next finished load). Changing only its recipients or channels clears nothing. An alert is written only while its rule still watches what the pass read, so a pass that read the rule just before the change raises nothing under it. A start clears the open alerts whose rule an earlier version turned off, deleted, or moved to another condition or source, each with its `cleared` event: the first start after the upgrade may send several at once. A load that kept no row (all filtered out, a header alone, or a zip, whose entries are loads of their own) neither fires nor clears a `rejected_share` rule. A source with no `rejected_share` rule alerts when a load finishes with failing rows (rejected for a reason other than `filtered`): once per load, counting only those rows, and again only when a Retry or a reprocess leaves more of its rows failing than its previous finish did (so a load whose failing rows were fixed alerts again if it fails later; a load finished before the upgrade is reported again at its first finish with failing rows, which may repeat rows an earlier alert reported); a load whose only rejected rows were filtered out raises nothing. An alert of this kind has no rule and nothing clears it: it stays open until retention purges it. One raised by an earlier version for a load whose rows were all filtered out is left as it is. Up to 0.2.0 both counted filtered rows as failures: a `rejected_share` rule now weighs fewer rows as failing on the same load, so a threshold raised to tolerate filtering may be lowered again. While an earlier version shares the store, the loads it finishes are judged its way. A source with no `unreachable` rule alerts after `delivery.alert_after_attempts`: one `delivery` alert per outage, not repeated while it is open. Delivery recovering clears every open `delivery` alert of the source, with a rule or without (on the REST path when HFS decides at least one entry of a batch; on the bulk path when a submission completes); the cleared alert is the recovery notice, and no separate `delivery_recovered` alert is raised any more. The first start of this version on a store closes the `delivery_recovered` alerts earlier versions left open, and the outage alerts that a later recovery notice, or a record of the source delivered after them, shows to be over; an older outage alert with neither stays open until the next successful delivery. Later starts leave outage alerts to their recovery. An open outage alert without a rule is kept by retention whatever its age.

#### The alert webhook

Each change of an alert is one **event**, `fired` or `cleared`, written in the same transaction as the alert itself, so neither is lost to a crash. The engine posts it to `alerts.webhook_url` as JSON:

```json
{
  "event_id": "5b0e5a8e-3c1f-4b7a-9a43-0f6f1d1c2e77",
  "event": "cleared",
  "alert": {
    "id": 12, "rule_id": 3, "kind": "rejected_share",
    "message": "Lab results: 83.3% of the rows kept from messy.csv failed, more than the 10% allowed (5 of 6)",
    "notify": ["ops@example.org"],
    "created_at": "2026-11-20T10:00:00.000Z",
    "cleared_at": "2026-11-20T10:05:00.000Z",
    "cleared_reason": "Lab results: labs.csv loaded with 0.0% failed, within the limit"
  },
  "source": {"id": "lab-results", "name": "Lab results"},
  "text": "[HIE] cleared: Lab results: labs.csv loaded with 0.0% failed, within the limit"
}
```

- `alert` holds these fields of the alert as `GET /api/alerts` lists it (`id`, `rule_id`, `kind`, `message`, `notify`, `created_at`, `cleared_at`, `cleared_reason`), with the same time strings, and nothing else: no delivery state; a `fired` event has `cleared_at` and `cleared_reason` null. `notify` is `[]` for an alert without a rule. `source.name` is null when the engine does not know it; `source` is null for an alert about no source. `text` is the field Slack and Teams incoming webhooks display.
- Headers: `Content-Type: application/json`, `X-HIE-Event-Id` and `X-HIE-Event` (the body's `event_id` and `event`), `X-HIE-Timestamp` (when this attempt was sent, in Unix seconds), and, when `alerts.webhook_secret` is set, `X-HIE-Signature: sha256=<hex>`: the HMAC-SHA256, under the secret, of the timestamp exactly as sent, a `.`, and the **raw body** (`{X-HIE-Timestamp}.{body}`), lowercase hex. The secret is trimmed of leading and trailing whitespace when read, so a secret file that ends in a newline signs with the secret it holds. Without a secret the events are unsigned. Use HTTPS: the signature proves who sent an event, not that nobody read it.
- **Verifying:** `X-HIE-Timestamp` is decimal digits only. A receiver computes the HMAC over that header's exact bytes, `.` and the body bytes it received, before parsing, and compares it with `X-HIE-Signature` in constant time; then it refuses a timestamp further than its **tolerance** from its own clock, in either direction. Use **5 minutes** (300 seconds) unless the two clocks are known to drift further; a wider window only lets a captured request be replayed for longer. Within the window a replay is caught by de-duplication on the verified body's `event_id` (below): a request stamped up to one tolerance ahead of the receiver's clock stays valid for two tolerances after it arrives, so keep each `event_id` acted on for at least **twice the tolerance** after the last request accepted for it, and for as long as acting on it twice would matter. Each attempt, a retry included, is a new request stamped and signed when it leaves, with the same body and `event_id`: the tolerance never has to cover the retry backoff, but de-duplication does. Trust the body, not the other headers. No release signed the body alone, so there is no older scheme to accept.
- **Retries:** any answer but a 2xx, a timeout (10 s; 3 s to connect) or a connection failure is a failed attempt. The engine tries again up to five times, waiting `alerts.webhook_backoff_ms` (from 1 to 3 600 000; 10 000 by default) and doubling each time: 10 s, 20 s, 40 s, 80 s, 160 s. Redirects are not followed: a 3xx is a failed attempt. Every attempt sends the same body, byte for byte, with the same `event_id`; its `X-HIE-Timestamp` and signature are those of the attempt.
- **De-duplication:** a receiver may get an event more than once (its 2xx was lost to a timeout, or an instance stopped before storing the outcome). It keeps the `event_id`s it has seen, answers a repeated one with a 2xx and does nothing else. `event_id` identifies one event and its retries, not a condition: a source whose lease lapsed in the middle of a pass can raise a second alert, with its own events, for the same condition.
- **Order:** a `cleared` event waits until its alert's `fired` event for the same URL has been delivered or given up on; a `fired` event still waiting for an earlier URL does not hold back a `cleared` for the current one. Still, a receiver may get a `cleared` for an alert it has not seen (fired before this engine version, while no URL was set, or whose `fired` failed), and a late `fired` after its `cleared` (a retry of an attempt that timed out): a late `fired` does not reopen a cleared alert. Match the two events of one alert by `alert.id`: an alert id is never given again.
- **One URL per event:** an event is sent only to the URL configured when it was written. After the URL changes, events still waiting for the earlier one stay `pending` (the API shows them `parked`) and go out if that URL comes back; a start without a URL leaves them waiting too. Rotating the secret signs waiting events with the new one; a blank secret is refused. Every instance on one store must have the same `alerts:` settings: any of them may send any waiting event, from oldest to newest, one at a time.
- **Delivery state:** `GET /api/alerts` answers `webhook: {configured, signed}` for this instance's settings, and each alert's `webhook`: its latest event (`event`, `event_id`), its `state`, `attempts`, `last_error`, `last_status` (the HTTP status of the last answer, null when there was none) and `delivered_at`; `webhook.events` lists every event of the alert, oldest first, with the same fields, so a `fired` parked for an earlier URL, or failed, is still seen once its `cleared` is delivered. `state` is `pending` (waiting for its first attempt, being sent, waiting for a retry, or a `cleared` waiting for its `fired`), `parked` (pending for another URL than this instance's), `delivered`, `failed` (five retries spent, or the last attempt recorded no outcome), `not_requested` (the rule's channels leave out `webhook`) or `not_configured` (no URL was set when the event happened). `webhook` is null for alerts recorded before events were. `last_error` is the error of the last **failed** attempt, kept after a later delivery, and a fixed sentence (`HTTP 503 Service Unavailable`, `timeout`, `connection failed`, `request failed`, `no outcome recorded for the last attempt`): never the URL or what the receiver answered. `last_status` is the HTTP status of the **latest** attempt, null while it runs or when it got no answer. A monitor that tracks delivery re-reads the alerts it still cares about (open ones, or ones not yet `delivered`): the state changes after the alert is listed.
- The webhook URL and secret never reach the log, the store or an answer; the store keeps a fingerprint of the URL to tell destinations apart. Events go out over HTTP/1.1. At `debug` and `trace`, the HTTP client logs the receiver's host and port when it connects. While `hie.yaml` gives `alerts:` any value, and whenever it is not valid YAML, its parse errors leave out every quoted value.
- The body before this version was `{text, feed, kind, alert_id, notify}` (and `cleared: true` on a clear), and a clear was posted even for a rule without the `webhook` channel. Receivers reading anything but `text` need the new fields.
